# 第4章 系统设计

## 4.1 系统架构设计

本系统采用前后端分离的B/S架构，整体分为三个层次：前端展示层、后端应用层和数据持久层。

**前端展示层**由基于Vue.js 2.6构建的单页面应用（SPA）承担，运行在用户的浏览器中，负责UI渲染、用户交互处理和数据展示。前端通过Axios发起HTTP请求与后端通信，所有业务数据的获取和提交都经由RESTful API完成，前端本身不直接访问数据库。Vue Router管理页面间的路由跳转，并通过导航守卫（navigation guard）实现登录状态验证和权限控制；Element UI提供统一的组件库支撑；ECharts负责图表渲染。

**后端应用层**基于SpringBoot 2.7.14构建，部署在服务器（或本地）的JVM中，对外暴露RESTful API接口。后端内部按照标准的三层架构组织：Controller层接收前端请求、完成参数校验和响应格式化；Service层封装业务逻辑，包括AI对话调度、数据统计聚合、错题复习计划生成等；Repository层通过Spring Data JPA与数据库交互。此外，系统还包含ZhipuAIService这一专门负责与智谱AI外部API通信的服务类，隔离了第三方依赖。

**数据持久层**在开发环境使用H2内嵌数据库（内存模式），应用启动时由DataInitializer类自动初始化测试数据；生产环境切换为MySQL 8.0，通过修改application.yml中的数据源配置即可完成切换，JPA的ddl-auto配置保证了实体结构变更的自动同步。

前后端之间通过HTTP协议通信，请求和响应数据均采用JSON格式，Content-Type为application/json。后端在CorsConfig中配置了跨域资源共享（CORS）策略，允许来自前端开发服务器（localhost:8080）的跨域请求。所有API请求统一以/api为前缀（由server.servlet.context-path配置），前端通过vue.config.js中的proxy配置将/api前缀的请求转发到后端服务（localhost:8081），避免了跨域问题对开发阶段的干扰。

系统整体架构可以用以下分层关系来描述：

```
浏览器（Vue.js SPA）
    ↕ HTTP/JSON（RESTful API）
SpringBoot 后端（Controller → Service → Repository）
    ↕ JPA（JDBC）
H2 / MySQL 数据库
    
后端 Service 层 → ZhipuAIService → 智谱AI GLM API（外部）
```

这种架构的好处在于：前后端职责边界清晰，可以独立开发、独立部署；后端API可以同时服务于Web前端，未来也可以支持移动端的接入；分层设计使得各层的代码改动对其他层的影响降到最低。

## 4.2 系统详细设计

### 4.2.1 用户认证功能设计

用户认证是系统安全的第一道防线，包含注册和登录两个环节。

**注册流程**：用户在Register.vue页面填写注册表单，包括用户名、密码、确认密码和邮箱。前端通过Element UI的el-form表单验证规则对输入内容进行本地校验（用户名长度3-20位、密码长度6位以上、邮箱格式正确、两次密码输入一致），校验通过后向后端发送POST /api/users/register请求。后端UserController接收请求后，先检查用户名和邮箱是否已存在于数据库中，若存在则返回错误信息；若不存在，则生成随机盐值，对密码进行加盐哈希处理后存入users表，并初始化用户的积分记录等关联数据，返回注册成功的响应。

**登录流程**：用户在Login.vue页面输入用户名和密码，提交后前端向POST /api/users/login接口发起请求。后端根据用户名查找用户记录，取出存储的盐值后对输入密码进行同样的哈希处理，与数据库中的密码哈希值比较。匹配成功则返回用户基本信息（id、username、nickname、role、targetPosition等字段，不包含密码），前端将其以JSON格式存储在localStorage中（key为"user"），作为后续接口调用时获取当前用户身份的凭据。匹配失败则返回"用户名或密码错误"的提示信息。

**路由鉴权**：router/index.js中通过router.beforeEach定义全局路由守卫。每次路由跳转前，守卫会检查localStorage中是否存在有效的用户信息；若不存在，则拦截跳转，重定向到/login页面；若存在，还会进一步检查目标路由是否带有requiresTeacher元信息（元信息是教师端路由的标志），如果目标是教师端路由但当前用户的role不是"TEACHER"，则拦截并跳转到/home/dashboard，防止权限越界。

用户认证的核心数据流如图4-1所示（文字描述版）：前端Register/Login页面提交表单数据 → UserController处理请求 → UserService执行密码校验/注册逻辑 → UserRepository完成数据库读写 → 返回用户信息给前端 → 前端存储至localStorage并跳转至仪表盘页面。

### 4.2.2 题库练习功能设计

题库练习功能涉及Question、TestRecord、AnswerRecord、WrongQuestionBook、QuestionFavorite等多个核心实体，整体流程设计如下。

**题目分类与筛选**：系统预设了Java、前端、数据库、算法、系统设计五个一级分类，每个分类下的题目又按难度（EASY/MEDIUM/HARD）做了标注。Question实体的category字段存储一级分类，subCategory字段存储二级分类（如Java下的"集合框架"、"并发编程"等），tags字段存储若干个标签（逗号分隔字符串），共同支撑多维度的题目检索需求。

**随机抽题逻辑**：用户在Test.vue选定分类后，前端向GET /api/questions/random?category=Java&count=10发送请求。后端QuestionService中的getRandomQuestions方法先从数据库中取出该分类下的全部题目，然后对列表进行shuffle（使用Collections.shuffle），取前count条返回。这种实现方式简单直接，对于中等规模的题库（几百到几千题）性能完全满足要求。

**答题与自动判题**：前端本地维护answers数组记录用户对每道题的作答选项。用户提交练习后，前端遍历每道题，将questionId和用户答案发送到POST /api/questions/check接口。后端对选择题通过字符串比较判断正确与否（单选题正确答案为A/B/C/D，多选题为AB、CD等组合字符串），对简答题和系统设计题返回参考答案供用户对比。判题结果连同正确答案和解析一并返回给前端，前端将每道题的判题结果渲染在答题详情区域。

**测试记录保存**：练习完成后，前端将本次测试的分类、总题数、正确题数、得分和用时等信息打包，向POST /api/test-records接口提交，创建一条TestRecord记录，供后续在成绩记录页面和学习报告中使用。

**错题自动入库**：在判题过程中，对于回答错误的题目，前端向POST /api/wrong-questions/add接口提交userId和questionId，后端WrongQuestionBookService中的逻辑先检查该题目是否已存在于用户的错题本中：如果已存在，则在原有记录上更新wrongCount（错误次数+1）；若不存在，则新建一条WrongQuestionBook记录，同时根据当前时间计算出nextReviewAt（当前时间+1天），设定第一次复习时间节点，完成错题的自动归档。

**收藏功能**：题目的收藏通过QuestionFavorite实体管理，收藏接口（POST /api/favorites/add）接收userId和questionId，服务层在写入前先检查是否存在同一用户对同一题目的收藏记录，若已存在则更新笔记内容，避免重复创建。取消收藏通过DELETE /api/favorites/remove接口完成，同时更新questions表中该题目的collectCount统计字段。

### 4.2.3 AI模拟面试功能设计

AI模拟面试是系统技术难度最高、差异化最显著的功能模块，其核心在于将大语言模型的能力融入到结构化的面试场景中，同时保证交互的流畅性和对话的连贯性。

**会话状态管理**：每次模拟面试对应一条InterviewSession记录，其中conversation字段以JSON格式存储完整的对话历史，结构为消息对象数组，每个消息对象包含role（"AI"或"USER"）、message（消息内容）和timestamp三个字段。status字段记录面试状态（ONGOING进行中/COMPLETED已完成/ABANDONED已放弃），duration字段在面试结束时写入本次面试的持续秒数。

**面试开始流程**：用户在Interview.vue填写目标岗位和面试类型，点击"开始面试"后，前端向POST /api/interview/start发送请求，携带userId、sessionType和position参数。后端InterviewService的startInterview方法创建新的InterviewSession记录，并根据面试类型调用generateGreeting方法生成开场白文本，将其作为第一条AI消息写入conversation字段，返回SessionId和初始对话内容给前端。前端拿到数据后，以气泡对话框的形式展示AI开场白，输入框出现，用户即可开始作答。

**多轮对话流程**：用户每次输入回答并发送后，前端向POST /api/interview/chat发送请求，携带sessionId和message。后端从数据库中读取当前会话的完整对话历史，提取最近10条消息（5轮对话）作为上下文，调用ZhipuAIService.generateReply方法，该方法构造出带有面试官角色设定的system prompt和上下文，向智谱AI的HTTP接口发起请求，获取模型生成的面试官回复。新的用户消息和AI回复都被追加到conversation字段并保存，返回给前端渲染。

system prompt的构造逻辑如下：基础部分描述AI的身份（"你是一位经验丰富的技术面试官"），岗位部分注入用户设定的目标岗位名称，面试类型部分根据TECHNICAL/BEHAVIORAL/HR分别注入对应的提问重点和风格要求，最后附上"保持专业、适当追问、不超过3个问题同时提出"等行为约束。这种动态构造system prompt的方式，使得同一个大语言模型能够在不同面试类型下表现出差异化的风格。

**面试结束与评分**：用户点击"结束面试"后，前端向POST /api/interview/end/{sessionId}发送请求，后端计算本次面试的时长，调用evaluateInterview方法对对话内容进行评估，生成总分和文字反馈（当前版本实现了基于规则的评估逻辑，评分在70-90分区间随机波动，反馈包含优点和改进建议的模板化文本），将结果写入InterviewSession并返回。前端根据返回数据跳转到面试报告页面（InterviewReport.vue），展示完整的面试统计和评估结果。

**面试报告设计**：InterviewReport.vue页面展示的内容包括：面试类型、目标岗位、开始时间和时长；综合评分展示（以大字号突出显示分值）；AI评价文本；完整的对话记录回顾（以对话气泡形式重现整个面试过程）。这些数据通过GET /api/interview/session/{sessionId}接口获取，用户可以通过成绩记录页面中的记录条目跳转到任意历史面试的详情报告。

### 4.2.4 知识库功能设计

**数据模型**：知识库由KnowledgeCategory（知识分类）和KnowledgePoint（知识点）两个实体构成。KnowledgeCategory存储分类的名称、描述和图标等信息；KnowledgePoint存储知识点的详细内容，其categoryId字段外联到对应分类，content字段以LONGTEXT类型存储Markdown格式的完整内容，difficulty字段记录难度级别，importance字段（整型，1-5）记录重要度，prerequisitePoints和relatedPoints字段以JSON数组形式存储前置知识点和相关知识点的ID，构成知识点之间的关联关系。

**学习进度追踪**：用户对每个知识点的学习进度通过StudyRecord实体记录，主要字段包括userId、knowledgePointId、progress（0-100的整数，代表进度百分比）、level（了解/熟悉/掌握三个枚举值）和studyTime。当用户在知识点详情页点击"了解"/"熟悉"/"掌握"按钮时，前端向POST /api/knowledge/study发送请求，携带userId、knowledgePointId、progress（了解对应30、熟悉对应70、掌握对应100）和level字段，后端检查是否已存在该用户对该知识点的学习记录，若存在则更新，否则新建。操作成功后系统自动刷新列表中的知识点卡片，在卡片下方显示对应的进度标签。

**内容渲染**：知识点的Markdown内容在前端通过markdown-it库（md.render方法）转换为HTML，并注入到v-html绑定的div中进行渲染，支持代码块、表格、有序/无序列表等Markdown标准语法的展示。

**收藏知识点**：用户在知识点详情页点击收藏按钮后，前端向POST /api/favorites/add发送type="knowledge"、itemId=知识点ID的请求，后端通过addFavoriteByType方法创建收藏记录。打开详情页时，前端还会并行调用GET /api/favorites/check-type?userId=&type=knowledge&itemId=接口，初始化收藏按钮的选中状态，让用户一目了然地知道当前知识点是否已在收藏夹中。

### 4.2.5 错题本与收藏功能设计

**错题复习计划**：WrongQuestionBook实体通过nextReviewAt字段记录下次建议复习时间，该时间点按照艾宾浩斯遗忘曲线的规律设置：第1次加入错题本时，nextReviewAt = 加入时间 + 1天；第1次复习后，nextReviewAt向后推2天；第2次复习后推4天；第3次复习后推7天；第4次复习后推15天。reviewCount字段记录已复习次数，每次用户在错题本中查看该题并主动点击"标记已掌握"时，系统更新reviewCount、lastReviewAt，并根据新的reviewCount值更新nextReviewAt。当reviewCount达到4次后，isMastered字段标记为true，该题从待复习列表中移除，但仍保留在错题本历史记录中。

**错题本展示与操作**：错题本页面（WrongQuestions.vue）的核心UI元素是一个带展开行功能的el-table。表格的每行对应一道错题，展开行后显示题目完整内容和用户的笔记。用户在展开行底部可以执行"添加/编辑笔记"和"标记已掌握"和"移除错题"三种操作，前两种操作通过调用PUT /api/wrong-questions/{id}接口更新记录，最后一种通过DELETE /api/wrong-questions/{id}删除记录。

**多类型收藏设计**：QuestionFavorite实体扩展了type和itemId字段后，可以通过(userId, type, itemId)的组合唯一标识一条收藏记录。type字段取值为"question"（题目）、"knowledge"（知识点）或"tutorial"（教程），itemId字段存储对应类型的数据ID。收藏夹页面（Favorites.vue）的loadFavorites方法从后端获取用户的全部收藏记录，然后在loadItemDetails方法中根据每条记录的type和itemId，分别向/api/questions/{id}、/api/knowledge/{id}或/api/tutorials/{id}发起请求，获取收藏项的标题和分类信息，填充到表格的对应单元格中显示。

## 4.3 系统数据库设计

### 4.3.1 系统E-R模型

系统共涉及10张核心数据表，各实体间的关系描述如下。

**用户（users）** 是整个系统的核心实体，几乎所有业务数据都以userId为外键关联到用户。一个用户可以有多条答题记录（answer_records）、多条测试记录（test_records）、多条错题记录（wrong_question_book）、多条学习记录（study_records）、多条面试会话（interview_sessions）和多条收藏记录（question_favorites），这些都是一对多的关系。用户还对应唯一一条能力模型记录（user_ability_model），是一对一关系。

**题目（questions）** 实体是题库的核心，被答题记录、错题本和收藏夹三个实体以外键引用。题目本身不直接关联到用户，而是通过createdBy字段记录是哪位教师创建的，属于弱引用（非强制外键约束）。

**面试会话（interview_sessions）** 通过userId关联到用户，每条会话记录存储了完整的对话历史（JSON格式的conversation字段），与用户是多对一关系。

**知识点（knowledge_points）** 通过categoryId关联到知识分类（knowledge_categories），通过study_records与用户建立间接关联，形成"用户对知识点的学习进度"的多对多关系（由study_records作为关联表）。

**收藏（question_favorites）** 通过userId关联到用户，通过type+itemId的组合关联到不同类型的内容（题目、知识点、教程），是一种多态关联设计。

**教程（tutorials）** 通过createdBy关联到创建它的教师用户，独立存储，学生端只读访问，教师端可以进行增删改操作。

E-R模型的核心关系图（文字描述）：

- users —（1:N）→ answer_records（userId外键）
- users —（1:N）→ test_records（userId外键）
- users —（1:N）→ wrong_question_book（userId外键）
- users —（1:N）→ study_records（userId外键）
- users —（1:N）→ interview_sessions（userId外键）
- users —（1:N）→ question_favorites（userId外键）
- users —（1:1）→ user_ability_model（userId唯一外键）
- questions —（1:N）→ answer_records（questionId外键）
- questions —（1:N）→ wrong_question_book（questionId外键）
- knowledge_categories —（1:N）→ knowledge_points（categoryId外键）
- knowledge_points —（1:N）→ study_records（knowledgePointId外键）
